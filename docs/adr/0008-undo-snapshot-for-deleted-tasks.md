# 0008. Снимок в памяти для отмены удаления задачи

- Статус: Принято
- Дата: 2026-11-04

## Контекст

- Удаление одной задачи должно быть обратимым. «Clear completed» отмену не предлагает.
- Достаточно одного уровня: в памяти хранится только последняя удалённая задача.
- Список уже пишется в localStorage по ссылке на `items` (ADR 0002). Документ хранилища — `{ version, tasks }` (ADR 0003). Снимок для отмены в эту схему входить не должен.
- Смена только снимка не должна вызывать запись. Появление и скрытие тоста не меняют сохранённый список.

## Решение

Состояние slice `tasks` в `src/features/tasks/tasksSlice.ts`: `{ items: Task[]; lastRemoved: LastRemoved | null }`. `LastRemoved` — `{ task: Task; index: number }`. Начальное значение `lastRemoved` — `null`.

- `remove` ищет задачу по `id`. Неизвестный `id` выходит сразу: снимок и `items` не меняются. Иначе reducer записывает `{ task, index }`, затем `splice` убирает задачу из `items`.
- `restore` при `lastRemoved == null` ничего не делает. Если `id` снимка уже есть в `items`, reducer только обнуляет `lastRemoved` и задачу не вставляет. Иначе вставка идёт в `Math.min(index, items.length)`, после чего `lastRemoved` становится `null`.
- `clearLastRemoved` обнуляет снимок и не трогает `items`. Повторный вызов при уже пустом снимке выходит сразу.
- `clearCompleted` отмену удалённых выполненных задач не сохраняет. Если снимок был, действие ставит `lastRemoved = null`. Выполненные задачи по-прежнему отфильтровываются из `items`. Когда нет ни выполненных, ни снимка, reducer выходит без изменений.

Снимок в localStorage не попадает. `saveTasks` по-прежнему получает только `items` и пишет `{ version, tasks }`. Предикат listener в `src/app/listeners.ts` остаётся `current.tasks.items !== previous.tasks.items`. Обнуление снимка само по себе ссылку на `items` не меняет и запись не запускает. `remove`, успешный `restore` и `clearCompleted` с выполненными задачами меняют `items`, поэтому список сохраняется.

Тост — свой компонент `UndoToast` (`src/features/tasks/components/UndoToast.tsx`), без библиотеки уведомлений.

- Корень с `role="status"`. Текст: `Task deleted` и кнопка `Undo`.
- Показ длится `5000` мс (`AUTO_HIDE_MS`), затем `dispatch(clearLastRemoved())`. Новый снимок сбрасывает таймер.
- При появлении тост фокус не забирает. Кнопка вызывает `restore`.

Пока `lastRemoved == null`, компонент ничего не рисует.

## Рассмотренные альтернативы

- **Мягкое удаление (`deletedAt` и список без таких задач).** Селекторы, схема хранилища и «Clear completed» начинают учитывать скрытые задачи. Для одного уровня отмены хватает снимка в памяти; схема ADR 0003 не меняется.
- **Библиотека тостов.** Для одной строки и одной кнопки зависимость не нужна. Своя разметка задаёт `role="status"`, срок `5000` мс и отсутствие переноса фокуса при показе.

## Последствия

- Плюс: отмена одного удаления — поле в состоянии Redux и три действия (`remove`, `restore`, `clearLastRemoved`). Версия хранилища остаётся 1.
- Плюс: скрытие тоста и `restore` при уже существующем `id` не пишут localStorage. Удаление и успешная отмена сохраняют актуальный `items`.
- Плюс: после перезагрузки незакрытый тост не восстанавливается. В хранилище нет поля, которого нет в схеме.
- Минус: уровень один. Следующий `remove` заменяет снимок; предыдущую задачу вернуть уже нельзя.
- Минус: `clearCompleted` сбрасывает висящий снимок. Отменить и одиночное удаление, и очистку выполненных после этого нельзя.
- Минус: позиция при `restore` — сохранённый индекс, обрезанный длиной текущего `items`. Это место в массиве на момент удаления, а не отдельная закладка, переживающая последующие вставки перед ним.
